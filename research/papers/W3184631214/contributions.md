# CRDTs for truly concurrent file systems (ElmerFS)

ElmerFS (HotStorage '21) is a geo-replicated, multi-master file system built on CRDTs, directly relevant to building an offline-capable, conflict-resolving distributed file system. Every data center replica serves reads and writes locally with no coordination; updates propagate asynchronously, so nodes operate during partitions (multi-master, eventual consistency via CRDT Strong Eventual Consistency). The FS is modeled with AntidoteDB CRDT types: directories as Remove-Win Sets of (ino, name, ViewID) entries, inode metadata as a Remove-Wins Map, file blocks and rename arbitrators as Last-Writer-Win Registers, all bundled into transactions per FS operation for atomicity (translation layer over FUSE).

Concrete guidance includes: handling the POSIX 8-byte inode-number constraint with a sharded global counter (ranges reserved per replica, numbers never recycled since recycling requires strong consistency); deletion semantics via remove-wins (delete all map keys) to avoid zombie partial inodes; and a novel name-conflict scheme: instead of silently renaming, concurrent same-name entries are distinguished by a per-user ViewID. The local user always sees their own file under the original name (partial name resolves to their ViewID first), while others see fully qualified names like `report.doc:Alice` — preserving intention and letting users fix conflicts with ordinary operations. For divergent renames it keeps a link RWSet (parent ino + FQN per link) plus an LWW register storing the authoritative parent, checked on lookup to suppress extra directory links. Open problems: rename cycles, orphan block CRDTs, permissions — addressed by proposing conditional transactions/post-conditions and tree CRDTs.
