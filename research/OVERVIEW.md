# Research Overview: Multi-Master, Offline-Capable Distributed File Systems

## Key findings so far

Twelve papers with full text have been reviewed (contributions.md written for each). The overall picture: no single system satisfies all requirements, but the necessary building blocks are well documented and combine into a coherent design for a small (≤10 node) multi-master, offline-capable file system.

### Architecture template

- **Coda** (W2124074197) established the template: local autonomy while offline (hoarding → emulation → reintegration), optimistic replica control, conflict detection at reintegration, and measured evidence that conflicts are rare under real workloads. It avoids cluster-wide consensus by design.
- **Ori** (W2078152492) is the closest end-to-end blueprint: fully peer-to-peer with no server, content-addressable storage with a commit DAG (Merkle tree), three-way merge against a merge-base, opportunistic pairwise sync via mDNS discovery, and grafting for cross-filesystem subtree moves.
- **Tofu** (W4392269970) is the strongest treatment of the topic's primary concern — directory rename/move conflicts — via a formal POSIX model (stat/data/names inode components), an exhaustive direct/indirect conflict taxonomy, CRDT-based convergence, and a session abstraction for legacy POSIX apps.
- **xFS** (W2025413686) shows how to distribute metadata and control among peers (manager map, log striping, hierarchical roll-forward recovery, consensus-based reconfiguration), though it assumes continuous connectivity.

### Conflict detection and resolution

- **Version vectors** are the standard detection mechanism; **Cox & Josephson / Tra** (W174158501) reduce storage to O(R+F) expected with *communication timestamps* and give principled handling of deletion-vs-absent conflicts. The **Ramsey & Csirmaz algebra** (W2145388050, Unison) specifies synchronization as command rewriting with pluggable resolution policies; its key trick — decomposing `move(a,b)` into `remove(a); create(b)` — makes directory moves tractable. **Syncpal** (W2948127449) adds the state-based alternative (snapshot diff + topological operation sorting + cycle breaking) and a precondition-based conflict taxonomy (Edit-Edit, Create-Create, Move-Move), iterated one resolution at a time.
- **CRDT approaches** (ElmerFS W3184631214, IMAP-CRDT/pluto W2794743700, layered types W2039852615) guarantee convergence by construction: remove-wins sets/maps for directories, LWW registers for metadata, ViewID-based partial name resolution (`report.doc:Alice`) to preserve user intent on name conflicts, and explicit orphan-handling policies (skip/reappear/root/compact) for concurrent delete-vs-child-update.
- **Bayou** (W2117260615, W2099184519, W2083398063, W2001803004) contributes application-defined conflict detection/resolution (merge procedures) and the anti-entropy propagation protocol with per-pair ordering constraints — the standard eventual-consistency propagation design.

### Cross-cutting lessons

- Conflict detection should use causality/history (version vectors or commit DAGs), never wall-clock timestamps (Ramsey & Csirmaz; Huston & Honeyman W1485389564 show version-number replay with preserve-both fallback).
- Moves/renames are the hard case: treat them across a formal namespace model (Tofu), decompose into create/remove (Unison/Syncpal), and break rename cycles explicitly (Syncpal, ElmerFS).
- Resolution should preserve data (preserve-both naming, deterministic generated names, orphanage/lost-and-found) rather than last-writer-wins.
- For ≤10 nodes, full replication of metadata (replicated namespace or prefix tables) is the right placement choice (Macko & Hennessey survey W4214919759); DHT/sharding machinery is unnecessary.
- File content conflicts are **not** merged at content level (requirement): conflicting contents must be preserved (keep both versions — AFS preserve-both naming, ElmerFS ViewID scheme).

### Tree move operations (new round)

- **Kleppmann et al., Extending JSON CRDTs with Move Operations** (W4394865965): a general move algorithm for CRDT trees/maps — moves interact correctly with concurrent non-move operations via a winner-based move validity check; prevents duplicates and cycles; introduces batched-move and lifecycle optimizations and is destined for Automerge.
- **Efficient Move in Geo-Replicated Trees** (W4221140037): coordination-free LWW move semantics for replicated trees; cycles arising from concurrent moves are resolved by a single deterministic compensation operation (undo of the causally-last move), avoiding the pairwise cycle-breaking of earlier work.
- **GlobalFS** (W2565376601, abstract only): strongly consistent alternative — atomic multicast plus per-site stores with four execution modes; shows what the optimistic design avoids (WAN latency, partition availability loss), and its remote-link mechanism is a reference for moves spanning namespace partitions.

### Round: Tier-1 cited-by papers

- **Optimistic replication survey** (Saito & Shapiro, W2295541535): the canonical map of the design space — six-layer architecture (semantic support, consistency unit, propagation, encoding operation-vs-state, conflict detection/resolution, scheduling); taxonomy includes *semantic* conflicts (individually valid, jointly invalid — e.g., moving a dir into its own subtree), and recommends defer-to-user/preserve-both resolution. Confirms version vectors over timestamps and pairwise anti-entropy for intermittent connectivity.
- **Merging semantics for conflict updates** (Tao et al., W2015055913): condensed citable version of Tofu's formal FS model incl. hard links; exhaustive direct/indirect conflict taxonomy; data-data conflicts resolved by preserving both versions; defines a correctness criterion for merged states.
- **What is a file synchronizer?** (Balakrishnan et al., W2085631457): specifies the two-phase decomposition (update detection | reconciliation) and makes "conflict" a property of the detection model — richer history metadata eliminates false conflicts; defines the semantics contract a synchronizer must publish.
- Abstract-only additions: **IMDfs** (W2945661666, modern version-tracking P2P personal FS; IEEE TPDS paywalled, no OA copy exists). **Guy et al., Replicated Data Management for Mobile Computing** (W2096689343): only the book's front matter is freely available (Springer Synthesis Lecture, paywalled full text) — stored as metadata; its subject matter is largely covered by Coda/Bayou/survey material already reviewed.
- Full text recovered via web search (mirrors): **Ivy** (W2071958655, OSDI'02) and **Pangaea** (W1984674591, OSDI'02). Ivy: log-per-participant architecture with hash-chained immutable records, version-vector conflict detection free of false conflicts, and delegation to application-specific resolvers; validates "mutation log + content addressing" as an alternative to CRDT state replication. Pangaea: symmetric peers with sparse replication, delta/harbinger propagation (measured ~2% overhead), and directory reconciliation via backpointers — an honest negative reference showing LWW + heuristics falls short on move conflicts.

### CRDT foundations (new round)

- **Delta-state CRDTs** (Almeida et al., W2295616151): delta-mutators return compact deltas carrying causal context (delta-intervals), so anti-entropy ships only recent partial state instead of full state — the right propagation substrate for a small peer set with Bayou-style anti-entropy; solves the state-based bloat vs. operation-based delivery-reliability trade-off.
- **Approaches to CRDTs** (W4402369907): a tutorial connecting CRDT theory to practice — state vs. operation based approaches and hybrids, OR-Set/MV-Register semantics (read returns concurrent versions → the keep-both behavior required for file contents), plus correctness criteria and implementation guidance.
- **CRDT overview** (Shapiro, W2810578094, abstract only): three-perspective framing (state-based, operation-based, delta) and the availability/scalability argument for coordination-free replication.

### Implementations and practical experience with tree-move algorithms (new round)

Web + OpenAlex survey of who actually implements the Kleppmann tree-move algorithm (W3206444683) and what practitioners learned:

- **Loro** (https://github.com/loro-dev/loro — ~6.2k★, MIT, Rust core with JS/WASM + Swift bindings, homepage loro.dev): the flagship production implementation. Its Movable Tree container is built directly on Kleppmann's algorithm; sibling ordering added via fractional indices (Figma-style) with peer-ID tie-breaking and jitter to handle concurrent equal indices (resetting indices when collision persists). The undo-do-redo machinery was kept because it mirrors Loro's Eg-walker event-replay core. Their blog (https://www.loro.dev/blog/movable-tree) is the best practitioner write-up: full taxonomy of move conflicts (move-vs-delete, move-to-different-parents, cycle-forming moves, ancestor-delete/descendant-move), a survey of how Dropbox ("conflicted copy") and Figma (server rejects cycle-forming ops; optimistic UI hides transient cycles — Weidner's CRDT survey https://mattweidner.com/2023/09/26/crdt-survey-2.html catalogs 6 cycle strategies) handle it, and benchmarks (10k random moves in 28 ms, M2 Max). Loro's own benchmark and the community one (https://github.com/Leeeon233/movable-tree-crdt) both find Kleppmann's algorithm faster than Evan Wallace's history-tracking "Mutable Tree Hierarchy" (https://madebyevan.com/algos/crdt-mutable-tree-hierarchy/) for realistic workloads — an independent Rust re-implementation with fuzz tests exists at https://github.com/mitkury/movable-tree-crdt-martin-vs-evan (Kleppmann: 10k moves in 9.9 ms vs Evan: 2795 ms).
  - Beyond the tree itself, Loro (1.0) demonstrates the full stack our design needs: version vectors + DAG frontiers as the sync currency, `export({mode: "update"/"snapshot"/"shallow-snapshot"})` incremental encodings (Git-style shallow clone to bound history growth), fast document loading via columnar encoding (borrowed from Automerge), time travel through history, and an Eg-walker-derived representation (from Joseph Gentle's Diamond-types) to keep CRDT metadata off the steady-state document. These map directly onto the "storage layer / propagation / GC" rows of our candidate architecture.
- **Automerge**: moves are currently delete+reinsert (the duplication bug from the tree-move paper). "Extending JSON CRDTs with Move Operations" (W4394865965, Da & Kleppmann 2024) implements proper moves in a Go prototype (https://github.com/LiangrunDa/AutomergeWithMove); planned for Rust Automerge. Practical lessons: per-op undo-do-redo must be batched; move-algorithm bookkeeping must be lifecycle-tracked so non-move ops don't pay for it; Jepsen-style randomized convergence testing is the accepted verification (instead of Isabelle). The **AMC model checker** (W4367675071) documents Automerge's real-world bug classes (disappearing writes, sync failures, concurrent-object-under-same-key issues) despite fuzzing.
- **CrossFS** (W4416409788, ACM TOS 2026): a FUSE filesystem that pushes FS *metadata* (not just docs) through CRDTs for cross-domain SEC; sparse-table/LSM storage, batching/async commits; shows the CRDT-metadata architecture works at production storage-engine level (though it does not solve the move-cycle problem).
- **Anjana et al.** (W4286307986) published a Golang/gRPC geo-replicated prototype and benchmarks vs Kleppmann (68× faster remote applies by replacing undo-do-redo with a single LWW compensation op).

Takeaway for the candidate architecture: Kleppmann's algorithm is the industry-default tree-move CRDT (Loro proves it production-viable); the two open engineering costs are (i) undo-do-redo under out-of-order arrival — mitigated by batching (Da/Kleppmann) or eliminated by compensation ops (Anjana), and (ii) log/GC discipline, still unsolved in most implementations.

## Candidate architecture (synthesis)

A coherent design for a ≤10-node multi-master, offline-capable DFS, assembled from the reviewed work:

1. **Storage layer — content-addressed Merkle DAG (Ori, W2078152492).** Immutable Tree/Blob objects hash-addressed with SHA-256; commits reference parent commits, giving each replica a full history and a natural merge-base for three-way reconciliation. Snapshots are cheap; replicas compare by exchanging hashes only. Corrupt objects are detected by hash and repaired by fetching from peers — fault tolerance by construction.
2. **Namespace/state model — formal inode model (Tofu, W4392269970).** Inodes split into *stat*, *data*, and materialized *names* components; hard links and directories modeled explicitly; FS invariants defined over the model; exhaustive direct/indirect conflict taxonomy, including indirect conflicts from concurrent directory renames (via causality between the rename that changed a path and later updates). Resolution rules are deterministic and never discard concurrent updates.
3. **Conflict mechanics — tree-move CRDTs (W4394865965, W4221140037) + CRDT directory types (ElmerFS, W3184631214; Martin et al., W2039852615).** Directory entries as remove-wins sets keyed by (parent, name); moves as CRDT move operations with winner-based validity or LWW + single compensation operation for cycle breaking; orphan handling with explicit policies (root/lost-and-found, reappear-as-ghost). Name conflicts resolved by per-replica ViewID/qualified names (`report.doc:Alice`); **file contents are never merged** — MV-register semantics keep concurrent versions side by side under distinct names (keep-both), matching the requirement.
4. **Reconciliation protocol — algebraic command reconciliation (Unison, W2145388050; Syncpal, W2948127449).** Update detection from history/snapshot diff; moves decomposed into create/remove; topological sorting of dependent operations with cycle breaking; iterative loop resolving one conflict at a time with replan — the pairwise primitive that any-to-any anti-entropy reuses.
5. **Propagation — anti-entropy with delta-CRDTs (Bayou, W2001803004; δ-CRDTs, W2295616151).** Pairwise, opportunistic, unordered pairwise sessions (Ori's orisync/mDNS discovery for finding peers); each session exchanges causal delta-intervals (recent partial state) rather than full state or fragile operation streams; ordering constraints per Bayou guarantee convergence regardless of session order. Version vectors or communication timestamps (Cox & Josephson, W174158501, O(R+F)) as per-file conflict metadata where DAG history is insufficient (e.g., deletes).
6. **Offline operation — Coda-style state machine (W2124074197; AFS replay, W1485389564).** Full local replica removes hoarding complexity (every node is a replica); offline writes either log mutating operations for replay (AFS) or apply directly to the CRDT state (Tofu/ElmerFS model) — the latter is preferred since convergence is guaranteed by the CRDT itself.
7. **Application semantics — session guarantees (Terry et al., W2125930899, abstract):** read-your-writes / monotonic reads per session to keep legacy applications sane on divergent replicas; Tofu's session abstraction (consistent snapshot + atomic merge at commit) as the stronger option.
8. **Failure handling (xFS, W2025413686):** durable local journal + fsync'd log before broadcast (pluto, W2794743700); recovery = replay from log and re-sync from any surviving peer; no consensus needed on the data path — roles (e.g., discovery) are re-electable, and with ≤10 nodes full metadata replication makes any node fully authoritative after a partition.

**Open questions:** (a) unify Tofu's indirect-conflict rules with the CRDT move semantics (whose move wins vs. whose resolution the user sees); (b) inode-number allocation for POSIX compatibility without strong consistency (ElmerFS's sharded counters); (c) how to expose keep-both file content conflicts in the UI/namespace with least surprise; (d) bounded growth of per-file version metadata over years of history.

### [Composing CRDTs Convergent by Construction](papers/W7215028644.json)

Conflict-Free Replicated Data Types (CRDTs) are abstract data types that ensure eventual convergence among data replicas in distributed systems. As they provide convergence out-of-the-box, CRDTs have become key building blocks for highly available, collaborative, and offline-capable systems, powering applications from real-time editors to distributed databases. Adopting an individual CRDT is straightforward, but real-world software routinely requires composing them. For example, an application might store a set of counters, combining a set CRDT with a counter CRDT. Unfortunately, classical CRDT theory does not guarantee that a composition of convergent CRDTs converges, forcing developers to reason about convergence again - the very burden CRDTs were introduced to remove. In this paper, we introduce a compositional framework for a broad class of operation-based CRDTs. It assembles CRDTs from five principal combinators -- Product, MapState, Associate, Traverse, and MapInterpretation -- each with built-in convergence guarantees. Any CRDT assembled from these combinators is itself a CRDT, preserving convergence by construction. This set is free of redundancy and subsumes previously proposed combinators. We develop the framework, its underlying theory, and its proofs entirely in Lean 4, producing a single artifact that serves as both the formal model and an executable, verified implementation. Our reusable library, Crdtlib, provides implementations and proofs for every combinator and CRDT in this paper. Our case studies (i) implement common CRDTs from Shapiro et al., (ii) apply the combinators in a complete application, and (iii) encode a JSON-structured tree CRDT as expressive as Automerge, with competitive runtime and memory use. These case studies show that developers can compose CRDTs without re-proving convergence for each composite.
